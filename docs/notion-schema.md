# DevDict Notion 데이터베이스 스키마 설계

이 문서는 `docs/PRD.md` 4장(Notion 데이터베이스 구조)을 실제로 Notion에서 만들 때 참고하는 실행
가이드다. `docs/ROADMAP.md` Task 009(Notion 데이터베이스 구축 및 통합 설정)를 진행할 때 그대로 따라가면
된다. PRD 4장이 "무엇을 만들지"(타입 수준)를 정한다면, 이 문서는 "정확히 어떤 이름·옵션값·설정으로
만들지"를 정한다.

## 0. 설계 원칙

| 원칙                        | 내용                                                                                                                                                                                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **속성 이름은 영어**        | `src/features/terms/api/notionMapper.ts`(Task 010)가 속성을 **이름 문자열**로 찾는다(`properties['Slug']`). 영어 이름은 오타·공백·전각문자 혼입 위험이 낮고, `types.ts`의 TS 필드명(`slug`, `category` 등)과 1:1로 예측 가능하게 대응된다.                 |
| **옵션 값은 한국어**        | Category·Tags 목록, Difficulty 3단계 값은 사용자에게 노출되는 콘텐츠이므로 한국어를 유지한다.                                                                                                                                                              |
| **값 집합은 데이터가 결정** | Category·Tags 옵션은 코드에 하드코딩되지 않는다(`docs/ROADMAP.md` Task 006이 조회 데이터에서 동적으로 파생). 따라서 옵션은 언제든 Notion에서만 늘려도 앱이 따라온다. 단 Difficulty만 `TermDifficulty` 유니온 타입으로 고정되어 있어 임의로 늘리면 안 된다. |
| **실패는 닫히는 방향으로**  | `Published` 체크박스는 새 행에서 항상 해제(`false`) 상태로 시작한다 — 초안이 실수로 공개되는 사고가 구조적으로 불가능하다.                                                                                                                                 |
| **Category ∩ Tags = ∅**     | 두 필터 드롭다운에 같은 단어가 동시에 뜨면 편집자와 사용자 모두 혼동한다. 값 집합이 겹치지 않게 설계한다.                                                                                                                                                  |
| **색상은 Notion 전용**      | `Term` 타입에 색 필드가 없으므로 Notion Select 색상은 앱 화면에 전달되지 않는다. 오직 Notion 편집 화면 가독성용이며, 앱 배지 색은 코드(Task 005/007)에서 별도로 정한다.                                                                                    |

## 1. 속성 9개 최종 설정값

DB 생성 직후 Notion이 기본 제공하는 `Name`(Title, 기본 라벨은 워크스페이스 언어에 따라 "이름"/"Name")과
`Tags`(Multi-select) 속성은 아래 표대로 개명하거나 그대로 재사용한다.

| #   | Notion 속성 이름 | 타입                              | 세부 설정                                             | 비고 / 주의사항                                                                                                                                                                                                                  |
| --- | ---------------- | --------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `Name`           | 제목 (Title)                      | 삭제 불가·필수                                        | 빈 제목 행이 생기기 쉽다(실수로 Enter). 매핑 레이어(Task 010)는 `title[]`이 빈 배열이면 해당 행을 스킵하고 dev 모드에서 경고한다. Notion은 제목 중복을 막지 않는다                                                               |
| 2   | `Slug`           | 텍스트 (Rich text)                | 규칙: `^[a-z0-9-]+$`, 소문자·하이픈만, 앞뒤 공백 금지 | **유니크 제약이 Notion에도 코드에도 없다.** 중복 시 `fetchTermBySlug`가 어느 페이지를 잡을지 비결정적이므로 §7 "슬러그 점검" 뷰로 육안 방어한다. `rich_text.equals` 필터는 공백까지 구분하므로 후행 공백 하나로 404가 날 수 있다 |
| 3   | `Summary`        | 텍스트 (Rich text)                | 권장 60~~120자(1~~2문장), 한국어                      | 카드에서 2줄 말줄임 처리(Task 005). 검색 대상이 Name+Summary뿐이므로(PRD 8장) 동의어·영문 표기를 여기 한 번 넣어두면 사실상 별칭 검색이 된다. 서식(볼드/링크)을 넣어도 plain_text로 평탄화되므로 넣지 않는다                     |
| 4   | `Category`       | 선택 (Select)                     | 시드 옵션 7개, 값은 한국어 — §2                       | 단일 선택 필수 입력 관례로 운영(비우면 필터 드롭다운에 빈 항목이 생김)                                                                                                                                                           |
| 5   | `Tags`           | 다중 선택 (Multi-select)          | 시드 옵션 12개, 값은 한국어 — §3                      | 기본 생성된 `Tags` 속성을 그대로 재사용 가능(이름이 이미 일치). 항목당 1~3개 권장                                                                                                                                                |
| 6   | `Difficulty`     | 선택 (Select)                     | 정확히 `입문`/`중급`/`심화` 3개 — §4                  | **옵션 값(라벨)을 바꾸면 `TermDifficulty` 유니온과 어긋나 매핑 레이어가 폴백 처리한다.** 4번째 옵션을 추가하지 않는다(코드 변경 동반)                                                                                            |
| 7   | `Published`      | 체크박스 (Checkbox)               | 새 행은 항상 해제(`false`)로 시작                     | 이 기본값이 곧 초안 보호 장치다. 프록시 필터 `{"property":"Published","checkbox":{"equals":true}}`의 유일한 근거이므로 **이 속성 이름을 바꾸면 전 사이트 노출 사고**로 이어진다                                                  |
| 8   | `Updated At`     | 최종 편집 일시 (Last edited time) | Notion 자동 관리, 수정 불가                           | 오타 수정 한 번에도 갱신되므로 "마지막 업데이트"가 곧 "내용 개정일"은 아님을 감안한다                                                                                                                                            |
| 9   | `Related Terms`  | 관계형 (Relation, 자기 참조)      | **`single_property`(단방향)**, 제한 없음 — §5         | 응답은 `[{id}, ...]` 페이지 ID 배열뿐(용어명 없음) → 목록 조회의 `pageId → Term` 맵으로 해석(PRD 4장). 맵에 없는 ID(비공개 용어)는 자동으로 렌더링에서 빠진다                                                                    |

### 만들지 않는 속성 (명시적 제외)

| 만들고 싶어지는 것          | 왜 만들지 않는가                                                                                                |
| --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `Body` / 본문 (Rich text)   | PRD 4장대로 본문은 **페이지 블록**이다. 속성에 넣으면 2000자 제한에 걸리고 블록 렌더러(Task 008)가 무의미해진다 |
| `Order` / 정렬순서 (Number) | UI 정렬은 클라이언트가 담당한다. 수동 순번은 항목이 늘수록 관리 비용만 커진다                                   |
| 조회수, 작성자              | PRD 6장 "제외" 범위                                                                                             |
| Unique ID                   | 접두사+숫자 형태라 슬러그를 대체하지 못하고, URL에 페이지 ID를 노출하지 않겠다는 PRD 8장 가정과도 무관하다      |

> 참고: 매핑 레이어는 이름으로 필요한 속성만 읽으므로, 위 9개 외에 편집 편의용 속성(예: 검토 체크박스)을
> 추가해도 앱은 깨지지 않는다. 단 이름이 9개 중 하나와 겹치면 안 된다.

## 2. `Category` (Select) — 시드 옵션 7개

**역할: "이 용어를 어느 지식 영역 선반에 꽂을 것인가."** 단일·배타적. "무엇에 관한 성질인가"는 전부
Tags로 보낸다.

| 순서 | 옵션 값 (한국어) | Notion 색상 | 포함 예시                                                   |
| ---- | ---------------- | ----------- | ----------------------------------------------------------- |
| 1    | 프롬프트         | Purple      | 메타프롬프트, 컨텍스트 윈도, 퓨샷 프롬프팅, 시스템 프롬프트 |
| 2    | 기획/문서        | Blue        | PRD, ADR, 유저 스토리, 요구사항 명세                        |
| 3    | 개발방법론       | Green       | MVP, 애자일, 스크럼, TDD, 기술 부채                         |
| 4    | 아키텍처         | Orange      | 헥사고날 아키텍처, MSA, 모놀리식, 관심사 분리               |
| 5    | 프론트엔드       | Yellow      | 하이드레이션, CSR/SSR, 번들링, 가상 DOM                     |
| 6    | 백엔드/인프라    | Brown       | REST, 멱등성, CI/CD, 컨테이너                               |
| 7    | 데이터/AI        | Pink        | RAG, 임베딩, 파인튜닝, 벡터 DB                              |

**구분 기준(Category vs Tags)**: 그 용어 자체가 그 분야의 핵심 개념이면 Category, 여러 분야를 가로지르는
성격·맥락이면 Tags. 예) `RAG` → Category `데이터/AI`; `메타프롬프트` → Category `프롬프트` + Tags `AI`.
카테고리가 8개 이상 필요해지면(예: "용어일반" 같은 분류 미정 도피처) 그때 추가한다 — 처음부터 만들지
않는다(코드 변경 없이 언제든 추가 가능하다는 P2 덕분).

## 3. `Tags` (Multi-select) — 시드 옵션 12개

**역할: "카테고리를 가로지르는 성격·맥락·학습 메타."** 채택 기준: ① 서로 다른 2개 이상의 Category에
걸쳐 쓰일 수 있는가, ② Category 옵션명과 겹치지 않는가. 둘 다 아니면 Tags로 만들지 않는다.

| 그룹      | 옵션 값 (한국어) | Notion 색상 |
| --------- | ---------------- | ----------- |
| 주제 교차 | AI               | Purple      |
| 주제 교차 | 협업             | Blue        |
| 주제 교차 | 문서화           | Gray        |
| 주제 교차 | 자동화           | Green       |
| 주제 교차 | 성능             | Orange      |
| 주제 교차 | 보안             | Red         |
| 활동/맥락 | 테스트           | Yellow      |
| 활동/맥락 | 배포             | Brown       |
| 활동/맥락 | 버전관리         | Default     |
| 활동/맥락 | 리팩터링         | Pink        |
| 학습 메타 | 약어             | Gray        |
| 학습 메타 | 헷갈림주의       | Red         |

항목당 1~3개 권장. 태그가 20개를 넘어가면 필터 드롭다운이 스크롤 지옥이 되므로 위 채택 기준으로 억제한다.

## 4. `Difficulty` (Select) — 옵션 3개 고정

| 표시 순서 | 옵션 값 | Notion 색상 | 의미 정의                                            |
| --------- | ------- | ----------- | ---------------------------------------------------- |
| 1         | 입문    | Green       | 배경지식 없이 정의만 읽어도 이해 가능                |
| 2         | 중급    | Blue        | 관련 기본 개념 1~2개를 이미 알아야 의미가 통함       |
| 3         | 심화    | Purple      | 실무 경험이나 트레이드오프 판단이 있어야 제대로 읽힘 |

Notion Select 옵션의 수동 순서(드래그)가 선택 드롭다운에 그대로 나타나므로 `입문 → 중급 → 심화` 순으로
드래그해 둔다. 초록→파랑→보라는 "얕음→깊음"의 단조 증가로 읽히고, 이미 보안 태그에 Red를 썼으므로
신호등(초록/노랑/빨강) 배색과 충돌하지 않는다.

**불변 계약**: 이 3개 옵션 값은 `TermDifficulty`(`src/features/terms/types.ts`)와 1:1이다. 값 변경·추가·
삭제는 코드 변경(유니온 타입 + 폴백 로직 + 필터 UI)을 반드시 동반한다.

## 5. `Related Terms` (Relation) — `single_property` 설정

**결론: `single_property`(단방향)를 쓴다.** 자기 참조 관계에서 `dual_property`(양방향)를 고르면 Notion은
같은 DB 안에 역방향 속성을 하나 더 자동 생성한다. 이때 매핑 레이어는 이름이 정확히 `Related Terms`인
속성만 읽으므로, **양방향으로 만들어도 그 역방향 속성은 앱 화면에 반영되지 않는다** — 편집 화면의 속성만
하나 늘어나는 순손실이다.

| 비교 항목                     | `single_property` (채택) | `dual_property`                  |
| ----------------------------- | ------------------------ | -------------------------------- |
| DB에 생기는 속성 수           | 1개 (`Related Terms`)    | 2개 (역방향 속성 자동 생성)      |
| 앱에 보이는 관련 용어         | 입력한 것만              | 동일(역방향 속성은 매핑 대상 밖) |
| PRD 4장 스키마(9개 속성) 부합 | O                        | X (10개가 됨)                    |
| 상호 링크                     | 양쪽에 수동 입력 필요    | 자동이지만 앱엔 무의미           |

### Notion UI 설정 절차

1. DB 우측 `+` → 속성 이름에 `Related Terms` 입력 → 유형에서 관계형(Relation) 선택
2. "데이터베이스 선택"에서 **이 DB 자신**(예: `DevDict 용어 사전`)을 선택 — 자기 참조이므로 같은 DB를 고른다
3. **"[DB명]에도 표시" 토글 → 반드시 OFF(해제)** — 이 토글이 곧 `dual_property` 여부다. OFF = `single_property`
4. **제한 → "제한 없음"** — `relatedPageIds`가 배열이므로 "1개 페이지"로 제한하면 안 된다
5. 관계 추가 확정 → 속성명이 정확히 `Related Terms`인지 최종 확인

> 주의: 3번 토글은 생성 시점에만 자유롭게 바꿀 수 있고, 나중에 바꾸면 이미 입력된 관계가 정리되는 부작용이
> 있다. 처음에 OFF로 만드는 것이 중요하다.

상호 링크를 원하면 두 페이지 모두에 `Related Terms`를 입력해야 한다(운영 규칙). §7의 "관련용어 점검"
뷰로 한쪽만 연결된 항목을 육안으로 확인한다.

## 6. 데이터베이스 이름

- **권장**: `DevDict 용어 사전`
- 대안: `개발 용어 사전 (DevDict)`

DB 제목은 워크스페이스 표시용이라 한글을 유지한다(API 계약과 무관 — 프록시는 `NOTION_DATA_SOURCE_ID`만
사용한다). §5-2단계에서 자기 자신을 검색해 고를 때 이름이 명확한 편이 실수를 줄인다.

## 7. 권장 뷰(View) 구성

코드가 보장하지 못하는 제약(슬러그 유일성, 필수 입력)을 뷰로 육안 방어한다. 뷰는 API 응답에 영향을 주지
않으므로 자유롭게 만들어도 된다.

| 뷰 이름       | 필터 / 정렬 / 그룹                                       | 목적                                            |
| ------------- | -------------------------------------------------------- | ----------------------------------------------- |
| 공개 목록     | `Published`=체크됨 / `Category`로 그룹 / `Name` 오름차순 | 실제 사이트에 나가는 것과 동일한 집합 확인      |
| 초안          | `Published`=해제됨                                       | 작성 중인 것만 모아 보기                        |
| 슬러그 점검   | `Slug` 오름차순 정렬, `Slug`·`Name`·`Published`만 표시   | 중복/빈 슬러그가 인접 행으로 붙어 눈에 띈다     |
| 입력 누락     | `Slug`/`Category`/`Difficulty` 중 하나라도 비어 있음     | Task 010의 "스킵+경고" 대상이 될 행을 미리 확인 |
| 관련용어 점검 | `Name` + `Related Terms`만 표시                          | 한쪽만 연결된 비대칭 관계를 육안 확인           |
| 최근 수정     | `Updated At` 내림차순                                    | 편집 이력 추적                                  |

추가로 페이지 템플릿 "새 용어"를 만들어 두면 좋다: `Difficulty` 기본값 `입문` + 본문에
`## 정의 / ## 왜 필요한가 / ## 예시 / ## 헷갈리기 쉬운 것` 헤딩 골격 — 본문 블록 구조가 균일해져
Task 008 렌더러 검증이 쉬워진다. (`Published`는 템플릿에서도 체크하지 않는다.)

## 8. Task 009 샘플 용어 9건 (비공개 초안 1건 포함)

Category 7종 전체, Difficulty 3종 전체, Tags 10종이 등장하도록 배치했다.

## 9. Task 009 실행 체크리스트

1. `DevDict 용어 사전` 데이터베이스 생성 (풀 페이지 DB 권장)
2. 기본 `Name`(Title) 확인, 기본 `Tags`(Multi-select) 유지, 불필요한 기본 속성 삭제
3. 나머지 속성(`Slug`/`Summary`/`Category`/`Difficulty`/`Published`/`Updated At`/`Related Terms`) 생성 — 이 문서 §1 표의 이름을 그대로 복사해 붙여넣는다(한글 IME로 영문 타이핑 시 자동완성 오타 주의)
4. Category 7개, Tags 12개(§2·§3), Difficulty 3개(§4) 옵션 시드 + Difficulty 드래그 정렬
5. `Related Terms` 관계형을 §5 절차대로 생성 (표시 토글 OFF / 제한 없음)
6. §7 뷰 6개 + "새 용어" 템플릿 생성
7. §8 샘플 9건 입력 — 9건을 모두 만든 뒤 마지막에 `Related Terms`를 연결(대상 페이지가 있어야 피커에 뜬다)
8. #1~#8만 `Published` 체크, #9는 해제 상태 유지
9. 통합(integration) 생성(읽기 전용 capability로 제한) → 이 DB에 연결 공유
10. `GET /v1/databases/{database_id}` → `data_sources[0].id` 확보 → `.env.local`에 `NOTION_API_KEY`, `NOTION_DATA_SOURCE_ID` 기입 (`VITE_` 접두사 금지)
11. 검증 쿼리: `POST /notion-proxy/v1/data_sources/{id}/query`, 본문
    `{"filter":{"property":"Published","checkbox":{"equals":true}},"page_size":100}` →
    **results 8건**(9건 아님)이면 스키마·필터·Published가 모두 정상
12. 화이트리스트 밖 경로(예: `GET /notion-proxy/v1/users`)가 차단되는지 확인
