# DevDict (개발 용어/개념 사전) — PRD

## 1. 프로젝트 개요

- **프로젝트명**: DevDict (개발 용어/개념 사전)
- **목적**: Notion을 CMS로 활용한 개발 용어·개념 미니 위키. 메타프롬프트, PRD, MVP처럼 실무에서
  자주 쓰이지만 정의가 흐릿한 개발 개념을 한 곳에 정리해, 개인 학습 기록이자 누구나 열람 가능한
  공개 레퍼런스로 제공한다.
- **CMS 선택 이유**: Notion API를 활용하여 비개발자도 콘텐츠 관리 가능. 용어 추가·수정이 Notion
  페이지 편집만으로 끝나므로 배포 없이 콘텐츠가 갱신된다.

## 2. 주요 기능

1. **용어 목록 조회** — Notion 데이터베이스에서 공개 상태인 용어를 카드 그리드로 표시
   (용어명, 한 줄 요약, 카테고리, 난이도, 태그 노출)
2. **필터링 및 검색** — 카테고리·난이도·태그로 목록을 좁히고, 용어명/한 줄 요약 대상
   클라이언트 사이드 키워드 검색 제공
3. **용어 상세 조회** — 슬러그 기반 상세 페이지에서 Notion 페이지 본문 블록을 렌더링하고,
   관련 용어로 이동할 수 있는 링크 제공

## 3. 기술 스택

- **Frontend**: React 19 + TypeScript + Vite 8 기반 SPA
  - 라우팅: React Router 8 (loader/action 미사용)
  - 서버 상태: TanStack Query v5 (쿼리 키는 feature별 `xxxKeys` 팩토리로 관리)
  - 클라이언트 전역 상태: Zustand 5 (테마, 사이드바 등)
  - HTTP: axios (`src/lib/apiClient.ts`의 인터셉터 규약 및 `ApiError` 형태를 따른다)
  - 토스트: sonner
  - React Compiler 활성화 상태이므로 습관적인 `useMemo`/`useCallback` 추가는 지양
  - 폴더 구조는 기존 feature 단위 구조(`src/features/<feature>/{api,components,hooks}`)를
    따르고, 본 프로젝트는 `src/features/terms/`에 구현
- **CMS**: Notion API (2026-03-11 버전, data source 모델 기준). Notion 통합 토큰은 브라우저에
  노출할 수 없고 Notion API는 CORS도 지원하지 않으므로, 프로덕션은 서버리스 프록시가 **필수**이다.
  Vite dev 프록시는 개발 전용이며 `configure`로 `Authorization`/`Notion-Version` 헤더를 직접
  주입해야 한다. 프록시는 (a) 지정된 data source 조회, (b) 블록 children 조회 두 엔드포인트만
  허용하는 화이트리스트 방식으로 구현하고, 클라이언트가 임의의 Notion 경로를 지정할 수 없게 한다.
  프런트엔드는 프록시가 제공하는 자체 엔드포인트만 알면 된다.
- **Styling**: Tailwind CSS v4 (`@tailwindcss/vite` 플러그인, CSS 변수 기반) + shadcn/ui
  (style: `radix-nova`, baseColor: `neutral`, `src/components/ui/`는 shadcn CLI가 관리)
  - 다크모드: `<html>`의 `dark` 클래스 토글 방식(기존 `useThemeStore` 규약 유지)
- **Icons**: lucide-react

## 4. Notion 데이터베이스 구조

| 속성명 (Notion, 영어) | 타입                             | 설명                                                                                                              |
| --------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `Name`                | 제목(Title)                      | 용어의 대표 이름 (예: 메타프롬프트)                                                                               |
| `Slug`                | 텍스트(Rich text)                | URL 경로에 쓰는 영문 소문자 식별자 (예: meta-prompt)                                                              |
| `Summary`             | 텍스트(Rich text)                | 목록 카드에 노출할 1~2문장 요약                                                                                   |
| `Category`            | 선택(Select)                     | 단일 대분류, 옵션 값은 한국어 (예: 프롬프트, 기획/문서, 개발방법론, 아키텍처)                                     |
| `Tags`                | 다중 선택(Multi-select)          | 교차 주제 키워드, 옵션 값은 한국어 (예: AI, 협업, 문서화)                                                         |
| `Difficulty`          | 선택(Select)                     | 옵션 값은 한국어 3단계 고정 — 입문 / 중급 / 심화                                                                  |
| `Published`           | 체크박스(Checkbox)               | 체크된 항목만 사이트에 노출 (초안 숨김용)                                                                         |
| `Updated At`          | 최종 편집 일시(Last edited time) | 상세 페이지의 "마지막 업데이트" 표시                                                                              |
| `Related Terms`       | 관계형(Relation)                 | 같은 데이터베이스를 가리키는 자기 참조 관계, `single_property`(단방향) (상세 페이지 하단 "관련 용어" 링크에 사용) |

속성 **이름**은 영어로 통일한다(코드가 `properties['Slug']`처럼 이름 문자열로 속성을 찾으므로 오타·공백에
안전하고 TypeScript 필드명과 1:1로 대응된다). 반면 Select/Multi-select **옵션 값**(카테고리·태그 목록,
난이도 3단계)은 사용자에게 노출되는 콘텐츠이므로 한국어로 유지한다. 실제 옵션 값 시드와 `Related Terms`의
Notion UI 설정 절차는 `docs/notion-schema.md`를 따른다.

용어 본문은 별도 속성이 아니라 각 Notion 페이지의 본문 블록(문단, 제목, 목록, 코드, 인용, 이미지)으로
작성하며, 상세 화면에서 이를 렌더링한다.

관련용어(Relation) 속성은 Notion 페이지 ID 배열만 반환하고 용어명/슬러그를 포함하지 않는다.
페이지당 추가 조회(N+1)를 피하기 위해, 목록 조회 시 이미 확보한 전체 용어를 `pageId → Term` 맵으로
만들어 관련 용어를 해석한다. 맵에 없는 ID(비공개 처리된 용어)는 렌더링하지 않는다.

## 5. 화면 구성

- **용어 목록 화면 (`/`)**: 상단 검색 입력 + 카테고리/난이도/태그 필터 컨트롤, 하단에 용어 카드
  그리드. 로딩 시 스켈레톤, 결과 0건일 때 빈 상태 안내를 포함한다.
- **용어 상세 화면 (`/terms/:slug`)**: 용어명, 카테고리/난이도/태그 배지, 최종 수정일, Notion
  본문 블록 렌더링, 하단 관련 용어 링크, 목록으로 돌아가기.
- **에러/Not Found 화면 (`*` 및 상세 조회 실패)**: 존재하지 않는 슬러그나 API 실패 시 한국어
  안내 메시지와 목록 이동 링크 제공 (에러 메시지는 `src/lib/errorMessages.ts` 규약을 따른다).

## 6. MVP 범위

**포함**

- 용어 목록 조회
- 카테고리·난이도·태그 필터
- 키워드 검색
- 용어 상세 조회 및 본문 렌더링
- 관련 용어 링크
- 로딩·빈 상태·에러 처리
- 기존 스타터킷의 다크모드·반응형 대응

공개여부 필터는 반드시 프록시(서버) 측에서 Notion query filter로 적용해, 비공개(초안) 용어가
클라이언트로 전송되지 않게 한다. 카테고리·난이도·태그·키워드 필터는 공개 용어 전체를 클라이언트로
받아온 뒤 클라이언트 사이드에서 수행한다 (용어 수가 수백 건 이하인 전제).

Notion API의 `page_size`는 최대 100건이므로, 프록시는 `has_more`/`next_cursor`로 내부적으로
커서를 순회해 전량을 모은 뒤 단일 응답으로 반환한다. "페이지네이션 없음"은 UI(무한 스크롤·페이지
번호)에 한정되며, 프록시 내부의 API 커서 순회와는 별개다.

인증 없이 누구나 열람 가능한 읽기 전용 서비스이며, 쓰기 작업은 전부 Notion에서만 이루어진다.

**제외**

- 로그인/회원
- 댓글·좋아요·즐겨찾기
- 사이트 내 편집 UI
- SSR/정적 생성 및 SEO 고도화
- 다국어
- 조회수 통계
- 무한 스크롤·서버 사이드 페이지네이션

## 7. 구현 단계

1. Notion 데이터베이스 스키마 확정 및 샘플 용어 5~10건 입력, Notion 통합 생성·DB 공유
   (읽기 전용 capability로 제한). `GET /v1/databases/{database_id}`로 `data_sources[0].id`를
   확보하고, 토큰 보관 방식(프록시 경유)과 환경변수(`NOTION_API_KEY`, `NOTION_DATA_SOURCE_ID`)를
   정의한다 (`.env.example`에 추가, `VITE_` 접두사로 토큰을 노출하지 않을 것). 모든 Notion API
   요청에는 `Notion-Version: 2026-03-11` 헤더를 고정한다.
2. 타입 및 데이터 계층 구현 — `src/features/terms/api/terms.ts`에 `termKeys` 쿼리 키 팩토리와
   목록/상세 조회 함수, Notion 응답을 앱 내부 `Term` 타입으로 변환하는 매핑 레이어 작성. 목록
   조회 결과로 `pageId → Term` 맵을 만들어 관련 용어(Relation) 해석에 재사용한다. 실제 연동
   전에는 기존 `src/mocks/` 규약대로 목 데이터로 선행 개발한다.
3. 용어 목록 화면 구현 — 카드 컴포넌트, 검색 입력, 카테고리/난이도/태그 필터, 로딩 스켈레톤과
   빈 상태 처리
4. 용어 상세 화면 구현 — 슬러그 라우팅, Notion 블록 → React 렌더러(문단/제목/목록/코드/인용/이미지).
   `has_children: true`인 블록은 재귀 조회하고, 블록 목록도 100건 단위 커서 순회로 전량 수집한다.
   관련 용어는 2단계의 `pageId → Term` 맵으로 링크를 구성하고, Not Found를 처리한다.
5. Notion API 프록시 연동으로 목 데이터 교체 — 공개여부 서버측 필터, data source 쿼리 커서
   순회, 429 응답 시 `Retry-After` 기반 재시도, 짧은 인메모리/CDN 캐시(예: 60초)로 분당 180회
   (3 req/s) 한도 대응을 구현한다. 이후 에러 처리·다크모드·모바일 레이아웃 점검 후
   `npm run build`/`npm run lint`로 최종 검증

## 8. 가정한 사항

- **슬러그 속성 추가** — Notion 페이지 ID를 URL에 노출하지 않기 위해 별도 텍스트 속성 가정
- **공개여부 체크박스** — 초안과 공개본 구분용
- **난이도 3단계** — 입문 / 중급 / 심화
- **카테고리(Select) + 태그(Multi-select) 분리** — 단일 대분류와 교차 키워드를 나누는 편이
  필터 UX상 유리하다고 판단. 하나로 합쳐도 무방
- **관련용어 자기 참조 Relation** — 사전 성격상 유용. MVP에서 부담되면 제외 가능
- **검색 범위** — 용어명 + 한 줄 요약만 대상 (본문 전문 검색 제외)
- **데이터 규모** — 수백 건 이하 전제. UI 페이지네이션은 두지 않되, 프록시가 Notion API의
  `page_size` 100건 한도를 커서 순회로 내부 처리해 전량을 모아 응답한다
- **SEO/SSR 제외** — 기존 저장소가 SPA 스타터킷이므로 MVP 범위 밖

## 9. MVP 이후 확장 (v2) — Notion 바로가기 링크

MVP(1~8장)는 완료되어 배포되었다. 이 장은 그 위에 얹는 아주 작은 증분 기능 하나를 정의한다.

- **배경**: 이 서비스는 인증 없는 완전 공개 읽기 전용 사이트이므로, 사이트 자체에 용어 추가/수정
  폼이나 쓰기 API를 넣지 않는다는 6장의 원칙은 v2에서도 그대로 유지한다. 다만 콘텐츠 작성자(운영자
  본인)가 새 용어를 추가하러 매번 Notion을 직접 찾아가는 대신, 사이트에서 한 번의 클릭으로 이동할
  수 있으면 편리하다.
- **기능**: 용어 목록 화면(`/`)에 "Notion에서 용어 추가" 같은 외부 링크 버튼(또는 아이콘 버튼)을
  추가한다. 클릭 시 새 탭(`target="_blank"`, `rel="noopener noreferrer"`)으로 Notion 데이터베이스
  페이지를 연다.
- **데이터**: 대상 URL은 Notion 데이터베이스 "페이지"의 공개 URL로, 통합 토큰처럼 비밀값이 아니다
  (다만 그 페이지 자체를 열람하려면 브라우저에 로그인된 Notion 계정이 해당 워크스페이스 멤버여야
  하므로, 실질적으로 운영자 본인 외에는 의미가 없는 링크다). 클라이언트 번들에 노출돼도 문제없으므로
  `VITE_` 접두사를 붙여 `VITE_NOTION_DATABASE_URL` 환경변수로 관리한다.
- **제외(v2에서도 유지)**: 사이트 내 용어 생성/수정 폼, 로그인/인증, Notion 쓰기 API(`POST /v1/pages`
  등) 연동은 여전히 범위 밖이다. 이 링크는 순수하게 "바로가기"일 뿐, 사이트가 쓰기 기능을 갖게
  되는 것은 아니다.
- **화면 위치**: 정확한 배치(헤더/사이드바/목록 상단 등)는 로드맵/구현 단계에서 기존 레이아웃
  컴포넌트(`Header`, `Sidebar`, `PageHeader` 등)를 검토해 결정한다.
